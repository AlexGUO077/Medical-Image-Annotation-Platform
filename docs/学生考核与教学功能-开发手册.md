# 学生考核与教学功能开发手册（V1.1）

日期：2026-10-26 初稿，2026-10-27 首版实施，2026-11-12 修订病灶考核、出题与对照流程。代码阅读基点：`971938c`，原分支 `fix/teaching-sample-annotation`。

本文记录本次新增学生功能的需求与工程目标。2026-10-27 用户授权按手册开发，首版按 D-46 的最小方案实施；实际完成与验证状态见 docs/STATUS.md，后续扩展不计入本次完成范围。现有源 Word《医学影像标注平台-开发手册（学生版）V1.0》中的“学生版”指开发手册的受众，该版本最初描述的是生产标注流程。

## 1. 需求来源与当前结论

### 1.1 用户已明确的目标

- 平台从标注内容生产扩展为具有教学意义的平台，新增学生身份。
- 学生独立阅片、逐个标注病变，选择身体部位、器官等信息，为标注对象撰写病变描述和报告。
- 作答时不可见病例已有报告和详细病例资料。
- 学生界面大体复用标注人员工作台布局，按考核用途修改。
- 学生信息提前录入；考虑由学生自行激活/注册、设置和修改密码。
- 开发阶段需要提供一个实际可登录的学生测试账号和密码。
- 本轮答复确认：提交后可查看教学版标准答案，同时需要评分和针对性反馈。
- 本轮进一步答复确认：参考报告随病例已有，第一版只需展示；分析学生回答与标准答案差异、自动生成建议与复盘可以后续实现。
- 2026-11-12 确认学生标注题均为有病灶病例。学生逐个标注发现的病灶，独立写出观察所见及可能疾病。每例随附的医生所见和诊断意见用于交卷后对照。
- 已确认：第一版全部先做对照展示，不自动评分；此前评分诉求移至后续阶段。

因此，第一版文字报告采用“学生报告与已有参考报告对照展示”，不把关键词相似度或未经验证的模型输出称为自动报告评分。第一版不实现客观自动评分；评分、自动差异分析与针对性建议后续单独定义。

### 1.2 与原范围的关系

源 Word §1.4 原定本期仅建设标注端、共享后端与数据库，不建学生画像和题库；§2.2 原定账号只有管理员、业务人员；账号采用管理员开通、无公开注册。用户本次明确提出的是对这些范围的新增需求，应作为后续范围扩展记录，保留原生产标注、脱敏、防下载和审核要求。

源 Word 的长期方向是一套后端、两个前端入口。建议第一版先在现有 React 应用内增加独立学生路由与业务模块，实现两个业务入口；若要求两个独立部署的前端应用，需在开工前确认。无论前端如何部署，数据和权限必须隔离。

范围与实施选择统一登记在 [D-46](decisions/D-46-student-teaching-scope.md)。后文保留设计时的“建议”和“拟”用于说明选择，首版实际采用方案统一以 D-46 与 education-api 契约为准，未采用的扩展不构成要求。

## 2. 仓库架构与实际业务链路

### 2.2 现有生产工作流

1. 管理员导入 DICOM/报告，或手工录入报告与关键图像；执行脱敏、人工确认，建立病例、序列、报告及附件。
2. 管理员维护临床资料、教学字段及病例疾病标签；按来源和系统创建任务，通过手动、自动或领取池分派。
3. 标注人员必须同时满足账号可用、系统资格和有效病例分派，才能读取工作台和影像。
4. 工作台返回病例信息、报告句子、序列与附件。标注人员画对象，填写部位、征象、置信度，关联报告句子。
5. 保存形成病例级新版本；提交检查对象与报告关联，结束标注分派，使病例进入待审核，并安排审核。
6. 审核通过锁定当前金标准版本并发布；打回重新分派。已发布病例库、抽检、下线、统计和导出沿各自权限运作。

以上链路由代码核对，不以 README 的历史“开发中”文字判断当前能力。`docs/STATUS.md` 仍是原 WP/SG 状态入口，本次方案不宣称新增功能通过现有安全门。

## 3. 建议采用的功能边界

### 3.1 第一版闭环

名册录入 → 学生激活/管理员准备测试账号 → 登录学生首页 → 打开分配的考核 → 阅片并独立标注 → 填对象描述与病例报告 → 保存 → 提交锁定 → 查看本人答案与参考内容。

组织端需要最小的出题、选择学生、查看提交、维护参考内容能力。建议先由管理员承担，不预先引入教师、课程、院系、多租户等体系；是否新增教师由用户确认。

第一版至少包括：

- 学生身份及与生产业务的双向权限隔离。
- 预录学生信息、激活与改密；本地测试账号可重复、安全地准备。
- 考核列表、单病例作答、保存状态、已提交记录及反馈页面。
- 四类绘制工具、序列/帧切换、窗宽窗位等现有能力的可复用部分。
- 病例级身体部位选择；对象级器官/位置、征象与病变描述；病例级学生报告。
- 独立草稿版本、提交快照、多人作答隔离、提交后不可改写。
- 提交后展示已有脱敏参考报告；有经过确认的标准标注时展示标准叠加。
- 第一版不计算分数、不生成自动评语；页面明确为自主对照。

不默认纳入第一版：自动理解自由文本报告、LLM 评语、客观自动评分、学习画像、排行榜、题目推荐、监考、复杂课程管理、邮件短信平台。后续需要时单独扩展。

### 3.2 权限矩阵

| 行为 | 学生作答中 | 学生提交后 | 组织人员 |
| --- | --- | --- | --- |
| 获准题目的影像 | 可读 | 按反馈访问有效期可读 | 按已有/新增明确授权 |
| 自己的标注与报告 | 可读写 | 提交快照只读 | 可读，不能冒充学生改写 |
| 已有参考报告、标准标注 | 不返回 | 可读教学反馈投影 | 可配置与核对 |
| 详细临床记录、病理附件、原始报告文件 | 不可读 | 不自动开放 | 沿既有权限 |
| 其他学生答案/成绩 | 不可读 | 不可读 | 仅有管理范围者 |
| 生产病例标注、审核、库检索、导出 | 不可访问 | 不可访问 | 沿既有权限 |
| 后续成绩修订（首版不实现） | 不可操作 | 不可操作 | 后续启用时记录修订人与原因 |

学生账号首版建议仅 student，不兼任生产 annotate/review。若确有同一人兼任需要，另行定义身份切换与答案暴露处理。

## 4. 学生工作台与业务细节

### 4.1 页面布局

继续使用 `WorkspaceLayout` 的左右栏伸缩、专注模式和中间影像区。

| 区域 | 学生端内容 | 需要移除/替换 |
| --- | --- | --- |
| 顶部 | 考核名称、匿名题号、保存状态、提交按钮 | 生产病例状态、包含临床内容的信息弹窗 |
| 左侧 | 作答说明、部位选择、学生报告编辑 | 真实报告、候选句匹配、详细病例与附件入口 |
| 中部 | 影像、工具栏、序列与帧导航 | 标准对象或答案预加载 |
| 右侧 | 新增病灶、本人病灶列表、选中病灶的器官/位置、征象、描述与帧范围 | report_sent_ids 关联要求、生产审核批注 |
| 提交后独立页 | 按所见与诊断两项分别展示学生原稿和医生原文，可查看完整参考报告、切换标准轮廓 | 继续编辑按钮、答案数据混入作答状态 |

**学生操作步骤**

1. 在“我的考核”打开一道题。通读题目说明，选择本例的身体部位，在影像区浏览获准的序列和帧。
2. 点右侧“新增病灶”，选择矩形、画笔、多边形或点，在图上完成绘制。画完后自动选中新病灶。填写该病灶的器官 / 位置、病变描述，可补充征象和帧范围。
3. 发现另一处病灶时，再点“新增病灶”。用画笔补画已选病灶会修整原掩膜；先点“新增病灶”再下笔会生成另一条记录，即使从已有轮廓内起笔。点击列表中的病灶，可回到对应序列和关键帧并继续编辑。列表中的编号、颜色与图上标记对应。
4. 在“我的阅片报告”汇总整例的影像所见和诊断意见。所见写下看到的表现，诊断意见写考虑的疾病及依据。对象描述与整例报告分别保存。
5. 提交前可保存草稿、返回再继续。缺少必填项时，提交按钮提示需补全的字段或病灶编号。提交后锁定答卷，在“报告对照”按项目阅读自己的原文与医生原文；有标准轮廓时可叠加查看。

每个病灶有独立 ID，文字随对应对象保存和删除。提交要求至少一个病灶，实际标注数由学生阅片判断。页面仅显示学生自己已画的个数，作答时不显示参考病灶数。

### 4.2 部位与器官

现有 part_id 是系统下的二级部位，未独立定义器官。建议先核对真实字典：若二级节点本身已是需要的器官粒度，可直接选用；若需要“胸部→肺”等两个维度，再增加最小的教育用器官选项/映射，不改变原疾病树层级。

学生选择是答案，必须与标准值分开存储。作答接口不能提前返回病例正确部位；字典也不能按该病例的正确器官过滤到只剩一个答案。每例选择一个身体部位；多个病灶可分别填写不同的器官或位置，也可在不同序列、不同帧标注。

### 4.3 保存与提交

- 保存采用 expected_version 乐观锁；冲突返回 409，禁止悄悄覆盖另一标签页内容。
- 保存对象、对象文字、病例级选择和报告作为同一作答版本，避免画面与报告不同步。
- 提交先完成保存，再在事务内核对本人、有效任务、当前版本及必填项，生成不可变提交快照。
- 双击或超时重试返回同一提交结果，不能重复消耗次数或生成两份成绩。
- 提交后不允许修改该次记录；后续重做需要新的 attempt，并保留已经看过参考答案的事实。
- 网络中断明确显示未同步；teacher_provided_teaching 来源不新增未经批准的浏览器持久化。刷新后恢复服务端最近保存版本，不能宣称未保存的内存内容可恢复。
- 草稿可暂时没有对象。最终提交须有至少一个病灶，每个病灶均已填写器官 / 位置和描述，整例已选部位并写完所见与诊断意见。旧版未交草稿继续编辑，旧版已交原稿只读保留。

## 5. 题目、参考答案与状态机

### 5.1 最小出题流程

管理员在“安排考核”中选择已确认脱敏、有影像的病灶病例。逐例核对影像有病灶且原报告记载了相应的医生所见和诊断意见（含可能疾病）。考核名称和作答说明对学生可见，应避免写入答案或病灶数量。

选中病例后可展开脱敏报告原文。常见标题下的“影像所见”和“诊断意见”会预填；无标题报告可从原文分别摘取两段。须保留医生原有的不确定性表述。缺少其中一项的病例应先完善源报告，再安排考核。提交发布时服务端逐例核对两段均来自当前报告，同一事务冻结原文、两段摘录和可用标准轮廓。旧题继续按发布时的原文对照，不回填后来的病例资料。

标准标注优先使用审核通过的金标准版本；未审核或尚在修改的对象不能自动充当标准答案。只有报告没有金标准的病例可以作为报告对照题，但不能计算病灶重合度。现有五例老师样例是否作为首批考题，需要先核对报告完整性、标准版本及来源授权。

### 5.2 版本与失效

- 发布教育题目时固定参考版本：题面白名单、序列范围、报告文本、标准对象、字典显示名；后续启用评分时再固定评分配置。
- 冻结必要文本/几何快照，不复制 DICOM 文件。病例后续修订不悄悄改变已交答卷的标准。
- 病例因安全原因下线，学生影像及参考访问同时停止；保留提交历史（后续包括评分历史），不因快照存在继续输出影像。
- 教育题目建议状态：draft → published → closed，必要时 revoked。
- 单次作答建议状态：in_progress → submitted；后续引入评价时将评价状态单列，避免评价故障回退已提交状态；首版不要求实现评价任务。
- 第一版建议一次提交即开放参考，重做能力另行确认；看过答案后再答不能等同首次考核。

## 6. 评价与反馈分阶段

### 6.1 第一版已经明确的部分

提交后显示学生原稿与病例已有参考报告，提供自主对照。参考展示不能命名为“系统已分析”或“自动诊断评价”。用户最新明确第一版全部先做对照展示、不自动评分。以下客观评分仅作为后续扩展设计，不属于首版开发或验收范围。

### 6.2 后续客观评分建议

| 维度 | 可用标准 | 可解释的结果 | 未具备标准时 |
| --- | --- | --- | --- |
| 身体部位/器官 | 经确认的标准选项及等价映射 | 正确、错误、漏选/多选 | 不评价 |
| 病灶定位 | 同序列、同坐标、同帧定义的标准几何 | 匹配、遗漏、额外对象；可选 IoU/Dice | 只展示、不计算几何成绩 |
| 征象等结构化选择 | 标准标签与允许答案 | 命中/遗漏及项目分 | 不评价 |
| 自由文本报告 | 既有参考报告 | 并排对照 | 不使用字符串相似度替代专业判断 |

实施前确定各项目权重、满分、部分得分、漏标/误标规则。缺失评价项不得未经定义就折算为满分或零分。

若纳入几何评分：box/polygon/brush 必须明确统一坐标与面积/掩膜计算口径；point 需另定距离容差，不能直接算面积 IoU；跨帧标注需确定按关键帧、指定帧集合还是全体积评价。不同工具表示不同目标时不强行比较。多个病灶采用一对一匹配，防止重复框同一病灶刷分；未匹配标准与作答对象分别记录漏标、误标。匹配阈值和计算版本应随题目固定。

### 6.3 后续自动报告分析

先定义有代表性的人工对照样本、专家认可的差异类别及验收指标，再决定规则、模型或混合方案。输出应关联具体学生句子和参考依据，区分遗漏、矛盾、表达差异及不确定项；保留人工修正入口。

现在仅在方案中描述评价结果的数据边界，不新增模型供应商、外部 API 或医学文本上传。后续模型选型、数据出域、费用和专业有效性需另行确认。

## 7. 数据与 API 工程草案

以下为逻辑模型；首版增量迁移为 StudentEducation1793059200000，具体字段与接口见 education-api 契约。

| 模型 | 最小字段/职责 | 约束 |
| --- | --- | --- |
| users 扩展 | role=student | student 不具有生产资格；继续账号状态、有效期和会话版本校验 |
| 学生名册 | 学号、姓名、可选班级、绑定 user_id、激活凭据散列/有效期/使用时间 | 学号唯一范围需确定；名册不能由学生任意创建；激活一次性并发安全 |
| 教育任务 | 标题、组织者、状态、开放/截止时间（可选）、反馈规则 | 已发布规则不能无痕改写 |
| 教育题目 | task_id、case_id、参考版本/快照、序列白名单、题面（评分配置后续增加） | 固定引用，不写生产状态；同病例可服务多个教育任务 |
| 学生任务关系 | task_id、student_id、可用状态 | 唯一关系，限制未被分配者访问 |
| 作答 | item_id、student_id、attempt_no、state、draft_version、答案、submitted_at | 每人每题每次唯一；更新需本人及有效状态 |
| 提交 | 提交快照、参考版本、提交时间 | 提交快照不可变；首版对照页据此授权 |
| 评价（后续，不建首版表） | 规则版本、分项结果、反馈、评价状态 | 评价失败可重试，修订保留来源 |

建议初期将有上限的作答对象与文字作为 JSONB 文档版本保存，复用几何解析；后续按检索需求决定是否拆对象表。必须明确对象数、文本长度、掩膜大小等输入边界，不能接收无界 JSON。

### 7.1 接口草案（均非现有接口）

| 接口 | 用途与权限 |
| --- | --- |
| `POST /api/auth/student-activate` | 名册绑定的一次性激活；请求不接受任意 role/quals |
| 既有 `POST /api/auth/login`、`POST /api/auth/password` | 扩展 student 类型；复用登录与密码策略 |
| `GET /api/education/tasks` | 学生只返回本人获准任务；组织端另设授权查询 |
| `POST /api/education/items/:id/attempts` | 创建/返回本人允许的作答，不允许自由指定别人的 student_id |
| `GET /api/education/attempts/:id/workbench` | 白名单题面、序列、本人草稿、状态；无参考报告或标准标签 |
| `PUT /api/education/attempts/:id/draft` | expected_version + 完整作答文档 |
| `POST /api/education/attempts/:id/submit` | expected_version；提交幂等且锁定 |
| `GET /api/education/attempts/:id/feedback` | 必须本人且已提交，按策略返回参考文本/标准对象及已有评价 |
| 教育管理接口 | 名册、题目、分配与提交查看；路径在管理身份明确后固定 |

帧服务沿用已有渲染与票据，新增教育访问模式并绑定 attempt/item、学生会话和题目版本；签发、读帧以及耗时渲染后均复核权限。客户端传 access_mode 不能自行赋权。

### 7.2 答案隔离检查清单

- 响应白名单覆盖工作台、列表、题目详情、序列元数据、附件、历史版本、错误详情及预加载请求。
- 不返回正确 system/part/disease 标签、reference IDs、报告句子或临床信息来辅助学生猜答案。
- 学生直接调用生产 workbench、cases、annotations、reviews、library/search、exports 必须拒绝；不以导航隐藏替代权限。
- 反馈访问依据服务端提交状态，不能由前端参数 unlock=true 解锁。
- 修改 URL 中的 case/attempt/student/series/version 不能跨学生、跨题目或跨版本取数据。
- 参考内容不得进入作答时的浏览器缓存、IndexedDB、HTML、日志、API 错误或前端 fixture。
- 保留水印、防原始影像下载、no-store 与审计；审计只记动作与引用，不记录报告全文、密码或激活码。

## 8. 学生账号与本地测试账号

### 8.1 建议账号流程

“自己注册”建议定义为“认领提前录入的身份”，不开放任意人员注册。组织人员录入学号、姓名及必要组织信息，生成一次性激活凭据；学生凭凭据设置自己的密码；激活成功绑定唯一 user_id。

仅凭学号和姓名不能证明本人，不建议作为唯一认领依据。首版可由管理员线下交接激活码，是否需要邮箱/学校认证待确认。激活失败统一提示并限流，服务端保存散列，码过期、已使用、并发重复认领均拒绝。

已有密码修改接口可以复用。忘记密码与首次激活是两个不同流程；现有账号管理没有通用密码重置，若纳入需增加管理员发起的一次性重置，不允许查回原密码。

### 8.2 用户要求的测试账号交付条件

账号属于首个可运行学生里程碑的必交付物，不以设计名称冒充已建账号。

- 拟登录名：`student_demo`，实际 user_id 以创建结果为准；避免随意硬编码 UUID。
- 完成 role 迁移、鉴权隔离与学生首页后，在当前本地开发库创建合成身份，密码随机生成，仅在本地私密渠道交接；不写入手册、seed 源码、Git 或日志。
- “影像阅片与病灶标注（合成练习）”包含 DX 与三帧 CT。每例影像有两个模拟目标，附两段合成参考文字与两个标准轮廓。复跑演示准备保留原任务、已有答卷和账号密码。
- 实际验证登录→进入学生首页→打开题目→保存→提交→看参考；确认该账号访问生产报告接口被拒。
- 重跑准备脚本不覆盖既有学生密码或答案；测试密码不能成为所有学生的默认密码。
- 交付时明确登录地址、登录名、凭据交接方式、是否首次改密、已分配题目与当前可用功能。

本次已建立 student 角色及本地 student_demo 合成账号，凭据只保存在忽略的 .credentials/student-education/ 目录。另一个 student_check 用于实际浏览器验证，不占用用户答卷。实际登录与绘制链路验证见本地证据；交付不使用 member 冒充学生。

## 10. 验证、迁移与交付

### 10.1 必测用例

1. 两名学生同时打开同一题，各自保存不同对象及文字，互不覆盖；修改对方 attempt ID 被拒。
2. 作答请求/网络响应中无参考报告、临床详情、标准对象与正确标签；直接访问旧接口同样被拒。
3. 正常保存、刷新重读、离线提示、旧版本冲突、多标签页冲突、保存后提交、未知提交结果重查。
4. 提交前请求反馈被拒；提交后可看指定参考，原始附件依然不可见；伪造 submitted 状态不能解锁。
5. 重复提交只产生一份结果；提交后旧草稿写入被拒；评价失败不丢提交内容。
6. 名册激活过期/重复/并发、学号唯一、越权设置 role、改密后旧会话、账号停用/过期。
7. 题目撤销、病例下线、任务截止与旧帧票据重放；渲染期间失效仍拒绝输出。
8. 参考更新不改变历史成绩依据；标准标签删除或病例修改按冻结/失效规则处理。
9. 同一题用画笔补画第一处，再新增第二处。为两处写不同描述，切换、保存、重新打开后分别核对几何与文字。零对象可保存草稿，提交应被拒绝。
10. 发布缺少所见、缺少诊断或引用非本例原文时应失败。提交后逐项对照，源报告变更不影响已冻结的内容。
11. 旧业务仍完成导入→生产标注→审核→发布→检索，原标注报告关联要求继续生效。

### 10.2 工程检查

沿用 Node.js 24.14.0 和现有 npm workspace。数据库迁移与接口 mock 先于页面逻辑；使用独立合成 schema 验证迁移，不在现有老师样例库上做全量回滚。

按变更范围执行单元、服务集成和浏览器验证；最终必要集成检查沿用 `npm run check`。权限、帧访问和迁移属于 HIGH 风险，实现阶段按 AGENTS.md 执行关键失败路径验证和必要只读审查。文档阶段仅检查引用、结构与 diff，不以未执行的软件测试宣称功能可用。

角色和教育表以增量迁移加入，更新数据库权限授予及验证脚本；不能只改初始建表文件。回退前先停用教育入口；已有学生与答卷时禁止删表或强行把 student 转成 member。旧版本程序不认识 student，应用回退与数据库保留策略必须演练。

交付包括：代码与契约、实际迁移验证、合成用例、学生测试账号、可复现登录/作答步骤、已实现与未实现功能表。原 WP/SG 不自动放行，人工验收和 Git 合并规则继续遵守。
