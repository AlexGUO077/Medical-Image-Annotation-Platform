## 1. 项目目标与边界

### 1.1 最终目标

建设一套部署在云端的医学影像标注平台，作为教学平台的内容生产线。标注人员在线阅片，使用拉框、涂抹、勾勒、点标记四类工具标出异常区域，并把每个标注对象与诊断报告中的句子建立关联。病例通过审核并发布后成为教学平台可读取的金标准病例。

平台必须同时交付以下四项能力，缺一不可：

1. 离线批量导入 DICOM 与诊断报告，并在导入时完成 DICOM 去标识化、报告人名遮蔽和人工复核；
2. 支持单帧影像和 CT/MR 多帧容积影像的精确、跨帧、报告关联和版本化标注；
3. 通过任务、资格、分派、审核和 10% 抽检形成可度量的生产质控闭环；
4. 不向标注人员提供原始影像下载能力，以帧服务、水印、限流、锁定和审计建立五道防线。

### 1.2 与教学平台的边界

- 最终形态是“一套后端、两个前端入口”：同一个 PostgreSQL 库、同一套后端服务，标注端和教学端是两个前端应用。
- 本期只建设标注端 `web-anno` 和共享数据底座。
- 学生画像、题库等教学平台专用表本期不建。
- `cases`、影像、报告、标注等共享表必须严格按第四章实现，教学平台将直接读取状态为“已发布”的病例。
- 标注端影像浏览能力应与教学平台共用同一渲染内核，保证“标注所见”与“学生所学”一致；共享方式属于待确认的工程契约，见第 13 节。

### 1.3 明确不支持或不在本期范围内

- 不支持动态超声视频。
- 不支持病理全切片 WSI。
- 不建设教学平台专用业务表与教学端页面。
- 不允许公开注册。
- 不提供面向标注或审核人员的原始 DICOM、整序列、可拼包分片或批量影像下载接口。
- 不允许用前端按钮控制代替服务端状态机或权限安全边界。

### 1.4 完成定义

项目只有同时满足以下条件才算完成：

- 第六章全部页面可用，录入 → 标注 → 审核 → 发布 → 检索全链路走通；
- 标注账号通过界面、抓包、API、URL 拼接均不能获得可还原的原始影像；
- 第四章表结构和第五章接口契约准确实现，字段命名与原文一致；
- 可通过 Docker Compose 在云服务器部署，提供 HTTPS，外部标注人员可实际访问；
- 导入 → 标注 → 审核 → 发布具备端到端测试，帧服务与权限具备单元测试。
- 安全与合规证据完整：上线前完成数据来源与授权核验、个人信息保护影响评估、数据分类分级、等保适用性/定级评估、威胁建模、安全测试、应急预案和恢复演练。本文只定义工程基线，不代替校方、数据提供方、法务或主管部门的正式合规结论。

## 2. 总体架构与信任边界

### 2.1 运行时结构

```text
外部浏览器
  └─ HTTPS 80/443
      └─ nginx（唯一公网入口）
          ├─ /api/*  → server:3000
          └─ 其余    → web-anno 静态资源

server（模块化单体）
  ├─ PostgreSQL 16：业务事实、状态、契约数据
  ├─ Orthanc：去标识化后的 DICOM，仅 server 可访问
  ├─ MinIO / 云 OSS：附件、帧缓存、导出包
  ├─ Redis 7：帧缓存、签名 URL 会话、限流、锁定、异步队列
```

### 2.4 全局工程约定

- REST 接口统一前缀 `/api`。
- JWT 有效期 8 小时；除登录外全部接口携带 `Authorization: Bearer`。
- 统一错误体：`{ code, message, details? }`。
- 分页参数：`page`、`pageSize`，且 `pageSize <= 100`；所有列表接口必须分页。
- 时间以 ISO 8601 UTC 存储，前端本地化显示。
- 状态、角色、工具等枚举值由数据库字典/契约驱动，前端不得用中文展示名参与逻辑判断。
- 所有业务表使用 UUID 主键并带 `created_at`、`updated_at`、`deleted_at`；删除采用软删除。审计日志“只增不删”优先于通用删除规则。
- 所有写操作必须在数据库事务内完成并写审计日志。
- `.env.example` 入库，真实 `server/.env` 不入库。

### 2.5 安全优先架构原则

安全不是 WP-17 的末期测试项，而是原文架构内所有工作包的前置约束；它不另起一套业务架构，也不授权修改原文功能和契约。任何功能设计同时给出授权规则、数据流、审计事件、失败方式和安全测试，否则设计不完整。

1. **默认拒绝**：没有明确允许规则即拒绝；接口、对象存储、Orthanc、管理路由和后台任务均不得依赖“前端不显示按钮”。
2. **服务端唯一裁决**：角色、资格、任务分派、病例状态、数据来源和资源关系由服务端基于当前数据库状态判定；JWT 中的展示性声明不能成为停用后仍有效的授权事实。
3. **最小权限和职责分离**：账号默认无任何系统资格和下载权限；管理员 2FA；导出申请人与审批人分离；他审的标注人与审核人分离。
4. **逐请求、逐资源鉴权**：每个请求按第 5.1 节固定顺序校验，并校验目标资源是否属于允许的病例、任务、序列和帧，防止越权与 IDOR。
5. **数据最小化**：只采集实现明确教学/标注目的所必需的数据；默认不把直接身份标识、原始报告、原始 DICOM 或可逆映射暴露给业务人员。
6. **原始数据受控区**：原始 zip 只进入隔离暂存区；完成恶意文件检查、解压限制、去标识化和烧录文字检查后，才允许写入正式 Orthanc/对象存储；原始暂存副本按批准时限安全清除。
7. **纵深防御**：HTTPS、内网隔离、应用鉴权、短时帧 token、水印、限流、账号锁定、审计和制度同时存在，任何单层失效不能直接暴露原始影像。
8. **加密与密钥分离**：传输全程加密；数据库、对象存储、备份和脱敏映射按数据等级实施静态加密；密钥不得写入代码、镜像、日志或普通数据库字段，并与密文分离管理。
9. **可追溯且防篡改**：安全日志与业务日志分离；审计记录只增不删、统一可信时间、最小化敏感内容，并具备完整性校验、访问控制和异常告警。
10. **来源与权利可证明**：每批影像、报告、附件和导出物必须能追溯数据提供方、授权用途、期限、使用范围和限制；来源不明或授权不完整的数据不得进入标注任务。
11. **安全失败**：认证、授权、脱敏、病毒扫描、签名校验、审计落库或密钥服务失败时默认阻断，不得为了可用性降级放行。
12. **真实数据最后进入**：开发和自动测试优先使用合成/匿名测试数据；只有安全门通过、授权记录齐全、环境隔离完成后才允许最小范围真实数据试运行。

## 3. 领域模型、身份与可见性

### 3.1 账号、资格、任务角色三层模型

| 层 | 值 | 含义 |
| --- | --- | --- |
| 账号角色 | `admin` / `member` | 管理平台能力与业务人员身份 |
| 系统资格 | `quals[system]` 中的能力 | 决定用户在某系统能做标注或审核；原文还提到可增设“录入”资格 |
| 任务角色 | `annotate` / `review` | 决定用户在某次任务中实际承担的工作 |

规则：

- 管理员开通、停用账号并按八大系统授予或挂起资格；无公开注册。
- 标注与审核资格按系统授予，任务角色必须与资格匹配。
- 自审要求同一人同时具备对应系统的标注和审核资格。
- 他审强制同一病例的标注人和审核人不同。
- 业务人员的工作可见性严格受任务指派限制。
- 已发布病例对持对应系统资格的人员开放只读检索，但不可下载、不可继续标注。
- 账号停用或到期必须立即失效并强制下线；资格挂起时在途病例自动释放回池。
- 管理员使用双因素认证；具体流程和接口待确认。

#### 鉴权实现基线

- 登录完成身份认证；后续每次请求仍须重新执行账号状态、资格、任务、资源和状态机校验，不能只验证 JWT 签名。
- 登录响应中的 `role/quals` 只用于界面展示和能力提示，服务端以当前数据库记录为授权事实来源。
- JWT 必须包含可撤销会话标识，如 `jti/session_id` 与 `token_version`；停用、到期、改密、资格挂起、异常锁定和管理员主动下线必须使现有会话立即失效。
- 所有资源接口必须从已授权的 `case_id` 反查允许的 `study_id/series_id/frame_index/attachment_id/annotation_id`，不得相信客户端提交的资源归属。
- 管理员、导出审批、账号/资格变更、密钥相关操作需要二次验证或近期认证；仅拥有 admin 字段不等于可以绕过双因素和职责分离。
- 认证失败不泄露账号是否存在；登录、改密、2FA、票据和审批接口分别限流并记录安全事件。
- 密码采用经评审的现代散列方案和独立随机盐；禁止明文、可逆加密、日志记录或邮件长期发送密码。
- 前端不得把可长期复用的凭证写入 URL、日志或不受保护的持久化存储；Bearer token 的浏览器存储方式属于 P0 决策项。
- CORS 使用明确源白名单；生产环境禁止通配源与凭证组合；管理端和普通业务端分别设置最小 CSP、HSTS、`nosniff` 和禁止嵌入策略。

### 3.3 病例状态机

```text
已录入 → 待分配 → 标注中 → 待审核 → 审核中 → 已发布
                    ↑          │          │
                    └── 打回 ──┘          └─ 下线 → 已下线

已下线病例可重新启用 → 待分配，并延续原版本历史
已发布病例另行生成 10% 抽检审核分派
```

状态是唯一事实来源，任何页面和接口都不得直接绕过状态机改数据。

关键迁移规则：

- 导入流水线完成后状态为“已录入”。
- 脱敏人工确认且病例进入任务后可转“待分配”。
- 标注提交前必须校验对象属性、征象标签和报告句级关联。
- 提交成功后由“标注中”转“待审核”，并自动生成审核分派。
- 自审派给原标注人；他审进入审核池或派给指定审核人，并排除原标注人。
- 审核通过后直接变为“已发布”，所有标注对象 `is_gold=true` 并锁定版本。
- 审核打回后回到“标注中”，保留批注；重交后重新激活审核分派。
- 已发布病例下线后教学端立即不可见；重新启用后回到“待分配”。
- 抽检失败触发该标注人员近期病例的全面复核。

### 3.4 一票否决项

以下任一项出现必须打回，不得放行：

- 脱敏不合格；
- 确诊依据缺失；
- 疾病标签错误。

## 4. 数据契约基线

### 4.1 通用要求

- 本节列出 16 张原文明确定名的物理表。
- 字段名、类型和必填性不得擅自更改。
- 迁移文件必须与表逐一对应；种子数据至少包括管理员、八大系统标签树和征象库初始数据。
- `report_sent_ids`、`quals` 等 JSONB 数组查询使用 GIN 索引。
- 原文未完整列出的约束、索引和外键只能作为内部实现补充，不能改变外部契约。

### 4.2 账号与权限

#### `users`

- `username / password_hash: varchar`：登录名与密码散列。
- `real_name / email / phone: varchar`：用于水印和审计。
- `role: varchar`：`admin / member`。
- `quals: jsonb`：如 `{"resp":["annotate","review"]}`，支持资格停用标记。
- `status / expire_at: varchar / date`：`active / disabled` 与有效期。

### 4.3 病例与影像

#### `cases`

- `case_no: varchar`：自动生成。
- `status: varchar`：`已录入/待分配/标注中/待审核/审核中/已发布/已下线`。
- `source: varchar`：自筹或合作机构名，必填且全程携带。
- `system_code: varchar`：八大系统编码。
- `disease_tag_id: uuid -> taxonomy_nodes`：默认单一主诊断疾病。
- `clinical_text / age_band / sex: text / varchar`：临床信息保存前自动脱敏。
- `confirm_method: varchar`：病理证实 / 随访确诊 / 临床综合诊断，必填。
- `teaching_fields: jsonb`：难度、适用层级、征象要点等，可后补。

#### `studies`

- `case_id: uuid -> cases`：一个病例可有多次检查，如平扫和增强。
- `study_uid / study_date: varchar / date`：`StudyInstanceUID` 是查重依据之一。

#### `series`

- `study_id: uuid -> studies`。
- `modality / series_uid: varchar`：`CR/DX/CT/MR/US` 与 `SeriesInstanceUID`。
- `orthanc_id / frame_count: varchar / int`。
- `default_window: jsonb`：CT 必填；标签缺失或多值时取第一个值并允许人工修正。

#### `reports`

- `case_id: uuid -> cases`；简版病例可无报告记录。
- `raw_text: text`：字段名虽为 raw，内容是脱敏后的报告全文。
- `sentences: jsonb`：`[{idx, text}]`，`idx` 是句级关联锚点。
- `mask_map_id: uuid`：指向加密存储的人名替换映射；目标表未定义，见第 13 节。

#### `attachments`

- `case_id / kind: uuid / varchar`：检查报告、病理、其他。
- `object_key / filename / size: varchar`：对象键、原始文件名、大小，单文件不超过 50MB。
- `deid_confirmed: bool`：上传人确认无患者标识。

### 4.4 标签体系

#### `taxonomy_nodes`

- `parent_id / level: uuid / int`：四级树“系统 → 部位/类别 → 疾病 → 分型/分期”。
- `name / synonyms / icd: varchar / jsonb`：ICD 可选。

#### `sign_tags`

- `name / system_code: varchar`：征象名和所属系统；征象库可跨系统共享。
- `definition: text`：定义和标注规范，工作台可随取随看。

### 4.5 任务与生产

#### `tasks`

- `name / source / system_code: varchar`：单一来源、单一系统。
- `review_mode: varchar`：`self / peer`。
- `priority / status: int / varchar`：进行中 / 已完成 / 已归档。
- `dispatch_mode: varchar`：用户于 2026-09-29 批准保存 `auto/manual/pool`；新任务默认 auto、存量保留 manual，见 [D-09/D-10/D-23](decisions/D-09-D-10-D-23-task-dispatch.md)。

#### `task_cases`

- `task_id / case_id: uuid`：病例加入任务后状态转为“待分配”。

#### `task_assignments`

- `case_id / assignee_id: uuid`。
- `task_role: varchar`：`annotate / review`，须匹配对应系统资格。
- `due_at / state: timestamp / varchar`：用于在途状态和逾期回收。

#### `annotation_objects`

- `case_id / series_id: uuid`。
- `tool: varchar`：`box / brush / polygon / point`。
- `geometry: jsonb`：DICOM 像素坐标下的框、RLE 掩膜、多边形或点。
- `frame_start / frame_end: int`：单帧影像二者相同。
- `window_preset: varchar`：CT 必填。
- `report_sent_ids: jsonb`：阳性描述必填；豁免或“报告未提及”必须显式表示。
- `part_id / confidence / measurements: uuid / varchar / jsonb`：置信度为典型/不典型。
- `version / is_gold: int / bool`。
- `created_by / task_id: uuid`。

#### `annotation_tags`

- `annotation_id / sign_tag_id: uuid`：标注对象与征象标签多对多；每个对象至少一条。

#### `reviews`

- `case_id / reviewer_id: uuid`。
- `result / comments: varchar / jsonb`：通过/打回与逐对象批注数组。
- `is_spotcheck: bool`：10% 抽检标记。

### 4.6 审计与导出

#### `audit_logs`

- `actor / action / target: uuid / varchar`：记录谁、何时、对何对象做了什么。
- `detail / ip: jsonb / varchar`。
- 只增不删，保存不少于 3 年。

#### `export_requests`

- `status / approver_id: varchar / uuid`：待审批 / 已批准 / 已拒绝；审批人必须是另一名管理员。
- `expire_at / url: timestamp / varchar`：批准后生成时效下载链接。

### 5.1 权限校验的固定顺序

所有接口依次执行：


## 7. 关键业务流水线

### 7.1 异步导入与脱敏

`POST /api/cases/import` 收到 zip 后立即返回批次号；队列逐病例处理，单个病例失败只记录失败明细，不中断同批其他病例。

固定步骤：

1. 解压并遍历 `.dcm`，按 `StudyInstanceUID / SeriesInstanceUID` 分组；
2. 以 `(source, study_uid)` 查重，重复则跳过并记录；
3. 清除或改写 `PatientName`、`PatientID`、`BirthDate` 等身份标签，保留窗宽窗位、像素间距等必要标签；
4. 首帧 OCR 检查烧录姓名/ID，命中则进入人工确认；
5. 去标识化后的序列写入 Orthanc，并写 `cases/studies/series`；
6. 报告做人名遮蔽、分句后写 `reports`；
7. 按 `BodyPartExamined` 和报告关键词预分八大系统，低置信度进入“待人工分诊”；
8. 病例状态设为“已录入”并写审计日志。

报告人名脱敏规则：

- 姓名统一替换为“某”，年龄数字保留。
- NER 与规则双路命中取并集；NER 可选 PaddleNLP UIE 或 HanLP。
- 常见称谓正则作为兜底。
- 替换映射加密存储，管理员可审计，业务人员不可见。
- 临床信息保存时调用相同函数，前端提示遮蔽数量。
- 人工点击“脱敏确认”后，病例才允许进入“待分配”。

### 7.2 报告分句与对象关联

导入时按 `。；;\n` 切分，去空白并过滤空句，索引 `idx` 从 0 开始。

候选句规则：

1. 使用对象的征象名、征象同义词、部位名组成关键词集合；
2. 按命中词数打分；
3. 含“未见/无/不除外”等前缀模式的句子降权，并纳入豁免判断；
4. 得分大于 0 的句子高亮，用户点击后写入 `report_sent_ids`。

提交规则：

- 阳性描述对应对象必须有关联句。
- 阴性句与鉴别句豁免。
- 报告确未提及必须显式标记“报告未提及”，不得以空数组含混表达。
- 附带发现照常标注和关联，但不新增疾病标签。

### 7.3 帧服务

申请票据：

1. 校验登录、账号状态和病例的工作指派或检索库资格；
2. Redis 按 `user_id + case_id` 计数，模态分别配置阈值；超限返回 429、锁定账号并告警；
3. 生成包含 `user_id/series_uid/frame_index/window/exp` 的签名 token，5 分钟过期；
4. 返回 token URL。

取帧：

1. 验签、验过期、验 token 用户与当前会话一致；
2. Redis 缓存命中则取缓存，否则从 Orthanc 取像素，按 window 渲染 PNG/WebP，缓存 30 分钟；
3. 输出前叠加账号、姓名、时间水印；
4. 记录用户、序列、帧号和时间审计。

红线：

- 服务端只接受 token，不接受可任意拼接的 `series_uid` 取帧 URL。
- token 与帧号绑定，改帧号必须失效。
- 绝不提供整序列包、原始 DICOM 或可拼包分片。

### 7.4 任务分发

- 每个任务只绑定一个来源和一个系统，任务间病例隔离。
- 自动派单默认选择具备资格且当前任务量最少的人员。
- 手动指派用于疑难病例。
- 标注池与审核池分开；按资格领取，领取即锁定，超时释放。
- 任务级在途上限和人员全局在途上限同时生效，取较小值。
- 管理员可因逾期或质量问题回收改派。
- 资格挂起时在途病例自动释放。
- 任务支持优先级。

### 7.5 保存、提交、审核和抽检

- 保存时整个标注版本号 +1，旧版本保留。
- 提交在单一事务内完成：校验对象完整性和资格、迁移状态、生成审核分派、写审计。
- 自审但原标注人无审核资格时阻断，并提示管理员改派。
- 审核通过：已发布、`is_gold=true`、版本锁定。
- 审核打回：标注中、保存逐对象批注、重交时复用/激活审核分派。
- 已发布病例按 10% 创建 `is_spotcheck=true` 的审核分派，资格规则等同他审。
- 抽检不通过时批量生成该标注人员近期病例的复核分派。

### 7.6 检索同步

- 检索条件至少包括系统、部位、疾病、征象、模态、来源和报告全文。
- 标签树四级浏览，结果卡片含缩略图、诊断和征象标签。
- 只返回当前用户有权限的病例。
- 发布或更新时同步 Elasticsearch，每日执行 PostgreSQL 与 ES 全量对账。
- 禁止把 PostgreSQL 和 ES 放入双写事务；PostgreSQL 是业务事实来源。

### 8.2 上线前八项安全检查

- [ ] 标注/审核账号遍历页面，无下载、导出、打印影像按钮。
- [ ] 抓包只发现 `/api/frames/{token}` 渲染图，无 DICOM 或可拼包分片。
- [ ] 帧 URL 5 分钟后、换账号或换会话访问均返回 403。
- [ ] 影像和附件预览水印完整且不妨碍诊断观察。
- [ ] 高速翻帧触发 429 和账号锁定，管理员可解锁，日志可查。
- [ ] 帧访问、标注、审核、发布、导出审批均能在审计日志查询。
- [ ] 外网无法访问 Orthanc、MinIO、Elasticsearch、PostgreSQL。
- [ ] 导出申请人不能自批，另一管理员批准后才生成有时效的链接。

### 8.3 其他安全硬约束

- 管理员双因素认证。
- 停用与过期即刻生效并强制下线。
- 影像原始像素除当前内存渲染需要外不得落到浏览器磁盘。
- 附件预览同样带水印。
- nginx 设置 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`。
- HTTP 全部 301 到 HTTPS。
- `/admin` 可选配 IP 白名单。
- 敏感操作至少包括发布、删除、导出、权限变更，并写审计。

### 8.4 数据分类与处理边界

| 等级 | 数据示例 | 默认处理规则 |
| --- | --- | --- |
| S4 严格受限 | 原始 DICOM、原始报告、直接身份标识、`mask_map`/UID 对照、密钥、未脱敏暂存包 | 仅隔离导入服务和极少数经授权管理员可接触；独立密钥、强审计、禁止进入日志/ES/前端；不得用于普通开发测试 |
| S3 高敏感 | 去标识化影像、脱敏报告、临床信息、附件、标注、病例与来源关联 | 医疗健康敏感个人信息方式保护；按任务/资格逐资源授权；加密存储和传输；导出须双人审批 |
| S2 内部 | 用户实名、邮箱电话、任务绩效、详细审计、IP、系统配置 | 最小角色访问；日志和看板去除不必要标识；禁止公开 |
| S1 可公开 | 已批准公开的无个人信息说明、静态前端资源、公开字典 | 发布前仍需内容和版权核验 |

数据级别由数据责任人批准并记录。不同级别混合时按最高级别处理；导出、备份、缓存、日志和搜索索引不得降低原数据等级。

### 8.5 数据全生命周期控制

1. **取得**：上传前登记数据提供方、合法处理基础、授权文件、允许用途、期限、范围和限制；缺一项则拒绝进入真实数据区。
2. **暂存**：上传到隔离区，使用随机对象键；限制压缩包总大小、展开大小、文件数、目录深度和路径穿越；执行恶意文件扫描；暂存区不被 web/nginx 直接访问。
3. **去标识化**：按 DICOM PS3.15 当前版记录采用的 Attribute Confidentiality Profile 与选项；默认清理私有标签，确需保留的私有标签逐项白名单；执行 Clean Pixel Data/烧录文字检查；报告和临床文本使用同一脱敏服务。
4. **复核入库**：自动检查和人工复核均通过后，才写入正式 Orthanc、PostgreSQL、MinIO 和 ES；原始包清除动作写审计，并可验证清除结果。
5. **使用**：任务、资格、来源、病例状态和用途共同约束访问；缓存、队列消息和临时文件只保存完成处理所需的最小数据。
6. **发布**：发布只改变受控平台内的可见性，不等于公开；教学端仍执行资格和只读控制。
7. **导出/共享**：先验证授权范围和接收方，再做最小字段选择、脱敏检查、双人审批、加密交付、时效链接和接收确认；默认不包含原始 DICOM。
8. **保留/删除**：为每类数据定义法律/协议要求、最短必要期限和删除/匿名化触发条件；备份、缓存、ES 副本和导出包同步执行；审计证据按其独立期限保留。
9. **事件处置**：发生或可能发生泄露、篡改、丢失时立即隔离、保全证据、阻断会话/密钥、评估影响并按责任单位批准的预案报告和通知。

### 8.6 鉴权与防下载强制矩阵

| 资源/动作 | admin | annotate | review | 已发布检索资格 | 额外条件 |
| --- | --- | --- | --- | --- | --- |
| 原始 DICOM/整序列 | 默认禁止直接下载 | 禁止 | 禁止 | 禁止 | 若依法授权的管理员导出确需影像，必须走独立双人审批且按 D-13 确认格式和脱敏级别 |
| 单帧渲染图 | 按管理职责最小开放 | 仅本人任务病例 | 仅本人审核病例 | 对应系统只读 | 5 分钟 token、会话/用户/病例/序列/帧/window 绑定、水印、限流、审计 |
| 去标识化报告 | 按职责 | 本人任务 | 本人审核 | 对应系统只读 | 永不返回 `mask_map` |
| `mask_map`/UID 映射 | 经单独授权的少数管理员 | 禁止 | 禁止 | 禁止 | 二次验证、用途理由、独立审计，不允许批量浏览 |
| 标注写入 | 管理员不因身份自动获得标注权限 | 对应资格 + 当前 annotate 分派 | 禁止 | 禁止 | 状态为标注中；对象归属、版本和事务校验 |
| 审核/发布 | 管理员仅执行明确管理动作 | 自审时还需 review 资格 | 对应 review 分派 | 禁止 | 他审排除原标注人；发布二次确认；一票否决 |
| 账号/资格/解锁 | 2FA admin | 禁止 | 禁止 | 禁止 | 近期认证、理由、前后值审计；高风险变更可要求双人复核 |
| 导出审批 | 申请人与审批人不同 | 禁止 | 禁止 | 禁止 | 2FA、范围与授权核验、时效、次数限制、完整审计 |

接口实现要求：

- 策略集中实现为可单测的授权服务/守卫，不允许各控制器复制并逐渐漂移。
- 鉴权查询采用不可绕过的服务层入口；后台队列、定时任务和内部 API 同样使用服务身份和最小权限。
- 对无权资源优先返回不泄露存在性的响应；日志保留内部拒绝原因和策略 ID。
- 帧 token 使用强随机或受认可算法签名，密钥轮换、算法白名单、恒定时间验签；禁止从普通 JWT 密钥直接复用。
- 任何“预签名 URL”只指向平台受控的单帧输出，绝不直接暴露 Orthanc/MinIO 对象键、桶名或内网地址。

### 8.7 数据来源、版权与使用授权

每个导入批次需要不可缺失的来源台账，至少记录：

- 数据提供单位、联系人、协议/伦理审批/授权文件编号及文件摘要；
- 合法处理基础和是否涉及单独同意、书面同意或依法无需同意的具体依据；
- 允许用途：标注、教学展示、科研分析、模型训练、对外共享、商业使用分别授权，不得相互推定；
- 使用地域、期限、人员范围、可否产生衍生标注、衍生成果归属、可否再许可；
- 原始影像、报告、附件、诊断术语、第三方内容各自的权利与限制；
- 撤回/到期/下线后的停止使用、删除、匿名化、已发布内容和备份处理规则；
- 导出接收方、目的、字段/影像范围、审批链和交付证明。

系统控制：

- `cases.source` 只表示业务来源名称，不能替代完整授权证据；需要独立、受控的来源批次/授权记录，具体表结构列为 D-31。
- 创建任务、发布、导出前均检查来源授权状态；授权过期、撤回或范围不覆盖时自动阻断。
- 页面水印、导出清单和审计使用数据来源/批次标识，但不得泄露患者身份。
- 未经确认不得把医学影像统一表述为“患者版权”“医院版权”或“平台版权”；系统只记录经审查的权利声明和合同边界。

### 8.8 安全开发与发布门

每次合并和发布至少执行：

- 威胁模型更新：信任边界、资产、攻击面、滥用途径和缓解措施；重点覆盖 IDOR、会话盗用、批量扒图、重放、越权导出、zip bomb、路径穿越、恶意附件、日志泄密和内部人员滥用。

- 证据归档：扫描报告、修复记录、测试输出、审批人、发布日期、镜像/依赖清单和回滚方案。

## 10. 推荐实施顺序与阶段门

### 10.1 强制工程原则

后续工程采用“**契约驱动、纵向闭环、逐门放行**”的建设方式。不允许先分别铺开全部数据库、后端或前端，再在末期集中集成；每一阶段必须产生可运行、可测试、可评审的纵向增量。

1. **源契约优先**：源 Word 定义产品的“做什么”，本基线定义“如何拆分和验收”；任何实现不得脱离两者。
2. **安全设计内建**：鉴权、脱敏、防下载、审计、加密和备份与业务代码同步设计和测试，不得留到功能完成后补做。
3. **契约先于实现**：先固定数据迁移、枚举、API 载荷/错误码、权限矩阵、状态机、DICOM 脱敏配置和标注格式，再由主代理按该契约实现前端、后端和测试。
4. **纵向闭环优先**：优先贯通一条真实的端到端链路，再横向扩充工具、模态、页面和统计能力，用最早闭环暴露跨层契约错误。
5. **高风险和难逆决策前置**：优先验证 DICOM 脱敏、帧服务、坐标/多帧一致性、任务并发锁、状态机、权限隔离和审计，避免在外围页面完成后才发现架构问题。
6. **服务端唯一裁决**：数据权限、资格、任务归属、状态迁移、资源关系和导出资格全部由服务端判定；前端路由和按钮只是交互提示。
7. **合成数据先行**：SG-0～SG-4 对应门未放行前只使用合成/匿名测试数据；真实数据只能在授权、脱敏、隔离、鉴权、防下载和审计证据齐备后最小范围进入。
8. **可观测与可追溯内建**：登录、看图、保存、提交、审核、发布、导出和管理操作在对应功能首次交付时即具备日志、指标和审计证据。
9. **行为验证、反向用例必须**：按 [AGENTS.md](../AGENTS.md) 验证，不强制每个工作包先写失败测试；源 Word §1.3 的数据库迁移和接口 mock 先于页面逻辑要求保留。权限和安全能力必须同时覆盖未登录、过期、错误角色、错误资格、未分派、跨资源和非法状态。
10. **证据放行**：没有可重复的测试输出、人工验收、契约核对和安全证据，不得宣称阶段完成，也不得进入下游阶段。

## 11. 测试与验收矩阵

### 11.1 单元与集成测试

- 权限校验顺序及 401/403/404 行为。
- 未登录、停用、过期、资格挂起、改密、异常锁定和管理员主动下线后的会话失效。
- 横向越权：用户 A 不得通过替换 `case_id/series_id/frame_index/attachment_id/annotation_id/task_id` 访问用户 B 资源。
- 纵向越权：member 不得调用 admin 接口；admin 也不能绕过具体业务资格、双人审批或状态机。
- 管理员 2FA 的绑定、验证、恢复、重放防护、限流和敏感操作近期认证。
- 报告人名脱敏双路合并、临床信息同函数处理、加密映射访问控制。
- DICOM 当前保密 profile/options 的标签清理、私有标签默认删除、必要标签白名单和 Clean Pixel Data。
- 隔离上传的 zip bomb、压缩比、文件数、路径穿越、符号链接、伪装扩展名和恶意附件测试。
- `(source, study_uid)` 查重。
- 签名 URL 生成、过期、重放边界、换用户/会话/病例/序列、改帧号/window 和密钥轮换。
- 模态化限流、锁定与解锁。
- 状态机所有合法迁移和非法迁移。
- 自动派单、上下限取小、并发领取锁、逾期释放。
- 自审双资格和他审人员分离。
- 报告句关联豁免与阻断。
- 四类 geometry 编解码、DICOM 坐标变换、RLE 往返。
- 版本递增、金标准锁定和下线后重启。
- 导出申请人与审批人分离、授权范围校验、最小字段导出、下载次数/时效和撤销。
- 审计字段最小化、敏感值遮蔽、完整性验证和审计写入失败时的安全阻断。
- 单元测试覆盖率不低于 70%。

### 11.2 端到端测试

主链路：

```text
导入 1 例 X 线 + 1 例 CT
→ 去标识化与报告脱敏确认
→ 建任务并分派
→ 四工具标注 + 报告关联
→ 提交
→ 审核通过
→ 已发布检索可见
```

附加链路：

- 打回 → 修改 → 重交 → 审核通过；
- 自审和他审；
- 10% 抽检通过与失败后全面复核；
- 下线 → 教学查询不可见 → 重新启用；
- 资格挂起和账号停用时在途释放/强制下线；
- 导出双人审批与链接过期。

### 11.3 安全测试

- 完整执行第 8.2 节八项并保留截图证据。
- 以标注账号遍历 UI、抓包、猜 API、改 token、拼 URL。
- 检查浏览器 Cache Storage、IndexedDB、localStorage、文件系统中无原始帧或整序列。
- 从公网扫描 Orthanc、MinIO、ES、PostgreSQL 端口。
- 核验水印可溯源但不遮挡诊断内容。
- 运行 SAST、依赖与许可证扫描、秘密扫描、镜像/IaC 扫描和 DAST；发布版本保留报告与软件物料清单。
- 由未参与实现的人员执行认证、访问控制、文件上传、注入、XSS、SSRF、跨域、令牌重放、并发领取和导出滥用测试。

### 11.4 性能测试

- 300 帧 CT 连续翻层无明显卡顿。
- 相邻帧预加载和缓存生效后响应 ≤200ms/帧。
- 所有列表分页且无全表返回。
- JSONB 数组查询命中 GIN 索引。
- 检索下推到 Elasticsearch/PostgreSQL，不在前端全量过滤。

## 12. 部署与运维基线

### 12.1 服务与端口

| 服务 | 方式 | 暴露 |
| --- | --- | --- |
| nginx | `nginx:alpine` | 公网 80/443，唯一入口 |
| server | Node 24 自构建 | 内网 3000 |
| web-anno | 静态构建产物 | 由 nginx 托管 |
| postgres | `postgres:16` | 内网 5432 |
| orthanc | `orthancteam/orthanc` | 内网 8042，仅 server |
| minio | `minio/minio` | 内网 9000；生产优先 OSS 私有桶 |
| redis | `redis:7` | 内网 6379 |
| elasticsearch | `elasticsearch:8` | 内网 9200，单节点即可 |

### 12.2 云端最低基线

- 单机起步建议 4 核 8GB，影像较多时单独挂数据盘。
- Let's Encrypt + certbot 自动签发和续期。
- nginx 仅配置 `/api/* → server:3000` 和静态前端两类公网路由。
- 上传体积建议按 2GB 配置 `client_max_body_size`。
- 生产、测试、开发使用独立账号、网络、存储桶、密钥和数据库；禁止复制真实数据到个人电脑或普通开发环境。
- PostgreSQL、Orthanc、MinIO、Redis、Elasticsearch 分别使用最小权限服务账号；禁止共享管理员凭证和默认密码。
- 秘密由专用秘密管理或受控部署变量注入；轮换过程可审计，泄露后可独立吊销，不依赖重新构建前端。
- 数据库、对象存储、数据盘和备份按最终分类分级/等保结论启用静态加密；备份密钥与备份介质分离。
- 主机、容器和依赖执行补丁时限策略；严重暴露漏洞在上线前关闭，运行中出现时按事件等级限时处置。
- 日志集中收集并限制访问；禁止记录 JWT、密码、2FA 秘钥、签名 URL 完整 token、原始报告、原始 DICOM 标签或 `mask_map` 内容。
- 生产管理访问通过受控入口、2FA 和来源限制；禁止把数据库、容器管理或 Orthanc 管理界面暴露公网。

### 12.3 备份恢复

- PostgreSQL 每日 `pg_dump`，保留最近 30 份。
- Orthanc 与 MinIO 数据卷每日异地 rsync，或使用 OSS 版本控制桶。
- 每月恢复到临时环境并抽查至少 3 个病例可打开。
- 恢复演练结果属于发布证据，不只是运维口头确认。

- 未批准偏差、口头偏差、无失效日期的“临时方案”和只写在聊天/代码注释中的决策均无效。
- 发现未决冲突时，暂停受影响工作包及其下游，但可继续与该冲突无共享契约和安全依赖的已批准工作。

### 14.5 GitHub 版本归档与回滚纪律

- 唯一项目远端为 `https://github.com/AlexGUO077/Medical-Image-Annotation-Platform.git`；具体流程以 `docs/GitHub版本管理与回滚规范.md` 为强制执行依据。
- 代码、测试、迁移、配置模板、依赖锁、部署文件、契约和技术文档的每个可评审版本都必须提交并当日推送；任务/会话结束前不得留下未上传的可保存版本。
- `main` 只保存通过验证的稳定版本。每个 WP/功能/修复/安全/文档变更使用独立分支和 Pull Request；禁止将功能变更直接推送到 `main`。
- PR 必须追溯源 Word 章节、本基线、WP、S 阶段和 SG 安全门，并附测试、安全检查和回滚证据；未通过上游门禁不得合并。
- 开发中进度通过远端分支和 Draft PR 监督。只有 GitHub 上的远端分支可解析到目标提交 SHA，才算该版本已归档。
- 禁止对已共享分支强制推送、删除或改写可审计历史。已共享变更使用 `git revert` 回退；含数据库迁移时必须同时验证 schema 和存量数据恢复。
- M1、M2、M3 阶段验收通过后分别对稳定 `main` 提交创建签名标签 `v0.1.0-m1`、`v0.2.0-m2`、`v1.0.0-m3`，作为稳定回滚点。
- 真实医学数据、患者信息、脱敏映射、生产日志/备份、密码、Token、私钥和真实 `.env` 不得进入提交、分支、PR、Issue、Actions 日志或 Release。
- 网络/GitHub 故障时可本地暂存已提交版本，但必须记录原因并在恢复后立即推送；未推送前不得宣称任务或阶段完成。

## 16. 下一步编码入口

当前不应一次性并行实现整个平台。正确入口是：

1. 先锁定源 Word 的功能、架构、表和接口契约，关闭会影响原文实现的第 13.1 节决策；
2. 按源文档构件和依赖顺序推进工作包，具体执行按 [AGENTS.md](../AGENTS.md)；WP-S0 补充既定构件所需的安全边界，不另行改造产品范围；WP-00 的已归档实现不因流程变更重做；
3. WP-S0 未放行前，工程环境只使用合成/匿名测试数据，真实数据入口保持关闭；
4. 完成 SG-0、SG-1 和 WP-00 健康/安全检查后，继续按源文档依赖进入 WP-01；
5. 每个工作包先对照源文档验收功能和架构，再验收安全控制；任一侧失败均视为未完成；
6. 所有后续实现都用“源 Word 功能与架构 → 本基线 → 工作包实现 → 功能契约证据 + 安全证据”的链路追踪；法律或强制性冲突单独升级确认。
7. 严格按第 10.2 节 S0～S12 实施；进入完整标注引擎前，先完成“合成 X 线+矩形标注”最小纵向闭环，但不将该窄切片当作全部功能完成。
8. 后续任务若与本基线不一致，必须先执行第 14.4 节变更/偏差处理；在获得明确批准并更新文档前，继续以本基线为实施和验收标准。
9. 新任务或上下文恢复时按 [AGENTS.md](../AGENTS.md) 定位必要小节并复用已核对内容；上游状态查 [STATUS](STATUS.md)，仅在缺失、过期或矛盾时定向核验，不以当前代码或未经核对的摘要推测需求。
10. 所有后续可评审版本必须按第 14.5 节在独立分支提交、推送并通过 PR 合并；每次任务交付同时报告本地/远端分支、提交 SHA、PR 和验证证据。

这样可以把架构调整限制在当前工作包及其直接下游，避免所有模块同时设计导致的大面积返工。
