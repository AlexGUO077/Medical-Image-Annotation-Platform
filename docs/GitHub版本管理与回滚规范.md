# GitHub 版本管理与回滚规范

> 适用仓库：`https://github.com/AlexGUO077/Medical-Image-Annotation-Platform.git`<br>
> 执行级别：强制<br>
> 核心目标：任何有意义的工程版本都能被监督、审查、对比和安全回滚。

开发期执行和证据规则统一见 [AGENTS.md](../AGENTS.md)；本文规定版本归档与合并要求。

## 1. 必须纳入 GitHub 的内容

以下变更一旦形成可评审状态，必须创建 Git 提交并推送到远端分支：

- 前端、后端、数据处理、部署和运维代码；
- 数据库迁移、seed、索引、枚举和数据字典；
- 自动测试、测试固定件、安全测试和性能脚本；
- Docker、nginx、CI/CD、监控、备份和恢复配置；
- 依赖声明及锁文件；
- 需求基线、API/数据契约、ADR、威胁模型、测试报告和变更记录。

构建产物、缓存、本地日志、运行数据和其他可再生成文件不应提交。“所有版本变更都上传”指每个有意义、可评审、可回滚的工程状态，不是每次键盘保存。

## 2. 分支模型

- `main`：稳定主线，只接收通过评审和验收的 Pull Request。
- `feature/wp-<编号>-<描述>`：工作包或新功能，例如 `feature/wp-02-auth-session`。
- `fix/<描述>`：缺陷修复。
- `security/<描述>`：安全加固或漏洞修复；分支名不得暴露未公开漏洞细节。
- `docs/<描述>`：纯文档、契约或治理规则变更。
- `chore/<描述>`：工程工具、依赖或非功能性维护。

分支必须从最新 `origin/main` 创建。禁止直接向 `main` 推送功能变更，禁止对已共享分支执行强制推送或改写历史。

## 3. 提交约定

提交使用小而完整的逻辑单元，一个提交只解决一个可说明的问题。提交类型为：

- `feat:` 新功能；
- `fix:` 缺陷修复；
- `security:` 安全控制或漏洞修复；
- `test:` 测试变更；
- `docs:` 文档和契约变更；
- `refactor:` 不改变外部行为的重构；
- `chore:` 工程和依赖维护；
- `revert:` 对已知提交的可追溯回退。

提交消息必须描述结果，不使用“修改代码”、“更新”等无法评审的表述。提交前必须审查 `git diff --staged`，确认没有患者数据、凭据、本地配置或无关文件。

## 4. 推送和 Pull Request

1. 按用户 2026-09-28 的 Actions 额度要求，以较完整、可评审的版本批量推送到对应远端分支。本地可保持小而完整的逻辑提交，但须集中完成实现、验证、审查和必要文档更新后一次推送；不为零碎进度、单独补记状态或证据链接反复推送。尚未形成完整批次时可保留本地提交跨会话继续，明确说明未推送状态；本条取代原逐提交当日及会话结束前强制推送要求。
2. 开发未完成时使用 Draft Pull Request 展示进度；未通过阶段门不得标记为可合并。
3. PR 必须写明源 Word 章节、需求基线章节、WP、S 阶段、SG 安全门、变更内容、测试证据、安全影响和回滚方案。
4. 源 Word §1.3 要求所有合并须另一人评审，权限、脱敏、帧服务改动须组长复核；至少一名非作者评审人批准且必需检查通过后才可合并。个人开发保留 PR 自审摘要，但自审和只读 agent 审查不替代上述人工要求及阶段门的指导教师/项目负责人复核；没有人工批准时保持待评审，不默认新增代理补位。
5. 远端分支存在目标提交且 GitHub 可读取该 SHA，才算版本已归档。只有本地提交、未推送分支或未录入 PR 的版本不得作为阶段完成证据。
6. 避免无必要的 Actions 重跑。先定位失败并完成本地修复与验证，再集中推送；确需重跑时优先受影响的失败作业，不反复重跑已通过且输入未变化的完整流程。不以节省额度为由绕过必需检查、降低安全阈值或替代人工批准。

网络或 GitHub 故障时可在本地暂存已提交版本，但必须记录原因，故障恢复后立即推送；未推送期间不得宣称任务或阶段完成。

## 5. 数据与凭据禁止项

以下内容严禁进入任何本地提交、远端分支、PR 附件、Issue、GitHub Actions 日志或 Release：

- 真实 DICOM、原始报告、患者/医务人员身份信息和未经批准的医学附件；
- UID/身份脱敏对照表、数据库导出、备份、事故现场数据和生产日志；
- 密码、Token、API key、私钥、证书私钥、真实 `.env` 和云服务凭据；
- 可用于重识别个人的截图、测试输出、错误堆栈或审计记录。

需要将合成医学数据用作自动测试固定件时，必须有明确的合成来源、无真实个人信息证据和专项评审，且只允许位于 `test/fixtures/synthetic/` 或 `server/test/fixtures/synthetic/`。

## 6. 里程碑与回滚

- M1、M2、M3 通过后分别创建签名标签 `v0.1.0-m1`、`v0.2.0-m2`、`v1.0.0-m3`；标签必须对应通过验收的 `main` 提交。
- 已共享提交的回退使用 `git revert`，不使用 `git reset --hard` 或强制推送破坏远端历史。
- 含数据库迁移的回滚必须同时验证代码、schema、存量数据兼容性和备份恢复，不允许只回退代码。
- 安全事故回滚不得恢复已泄露密钥或失效凭据；必须先轮换凭据再恢复服务。

## 7. 每次远端归档的证据

- 本地分支名和完整提交 SHA；
- GitHub 远端分支和能解析到同一 SHA 的证据；
- PR 链接、状态、评审人和合并提交；
- 测试、构建、契约核对和安全扫描结果摘要及对应提交的 CI run/必要 artifact 链接；本地独有验证附命令、环境和简短结果，不复制全文转录；
- 回滚方案和影响数据说明；
- 对应的 WP、S 阶段和 SG 安全门。
