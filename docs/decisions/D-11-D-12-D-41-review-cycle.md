## 首批范围

审核只读阅片、逐对象/总体批注、三项一票否决检查、通过即发布并锁定当前金标准版本、打回重标及重交。下线/重新启用和抽检另补契约；首批不代表 WP-11 或 SG-5 完成。

不增加业务表、独立发布审批、敏感操作二次 2FA、审核草稿平台、对象级通过状态或复杂原因枚举。数据库既有 reviews 与标注多版本结构足以承载首批；若实现发现必须变更 schema，先登记并确认，不修改已合并迁移。

## D-11：审核请求和批注（建议）

- 唯一结论接口采用源 Word 接口总表更详细的 `POST /api/reviews/{caseId}`。
- 请求为 `{ expected_version, result, comments }`；result 仅允许数据库既有值“通过”或“打回”。expected_version 复用现有乐观并发方式，必须等于当前提交版本。
- comments 恰有一条 `kind=checks` 的三项布尔检查记录；其余为 `kind=object` 或 `kind=overall` 的文字批注。对象引用采用已有跨版本稳定 logical_id，仅允许本病例被审核版本中的对象。总体意见不伪造对象引用。
- 通过要求脱敏、确诊依据、疾病标签三项全部为 true；未填写或任一 false 不允许通过。打回必须至少一条非空、可执行的对象或总体意见；前端提示禁止填入身份信息，审核服务不接收原始材料。
- 请求不得指定审核人、时间、状态、is_gold 或任意其他字段。服务器为持久化批注补充 reviewer_id、created_at、annotation_version；复用 reviews.comments JSON，不新增字段表。
- 通过和打回都只针对当前版本；状态、分派、审核记录、金标准和审计同一 PostgreSQL 事务。审核本身不递增标注版本，也不修改历史轮廓。

示例（字段结构待确认；对象 UUID 仅为合成示例）：

```json
{
  "expected_version": 3,
  "result": "打回",
  "comments": [
    {
      "kind": "checks",
      "deidentification": true,
      "confirmation_basis": true,
      "disease_label": false
    },
    {
      "kind": "object",
      "annotation_id": "00000000-0000-4000-8000-000000000001",
      "text": "请核对疾病标签，并调整该对象的报告关联。"
    }
  ]
}
```

## D-12：审核读取的最小补齐（建议）

- `GET /api/reviews/{caseId}?version=...` 供审核台读取当前/指定历史版本的标注、最小病例信息、疾病标签、脱敏报告句、序列与附件清单、任务审核模式，以及最近一次审核批注。版号省略表示当前版；历史版号校验复用已有版本语义。
- 必须是本人的有效审核分派、对应系统审核资格、病例“审核中”；自审保留双资格，他审排除当前提交人。管理员没有阅片旁路。读取不改变业务状态；缓存使用 no-store/private。
- 审核附件使用 `GET /api/reviews/{caseId}/attachments/{attachmentId}/preview?page=...`；沿用现有已确认附件的水印分页 PNG 与存储读取后二次鉴权，不开放原件下载。
- 帧仍走已有 ticket/PNG 接口及审核分派鉴权，不新建图像通道。只允许 synthetic 首批链路；已有老师样例来源许可不自动扩大到发布。
- 打回后原标注人从既有 `GET /api/cases/{caseId}/annotations` 响应新增的 `latest_review` 获取最近批注；权限仍是本人有效标注分派。批注引用的旧版对象已删除时，只展示历史意见，不冒充当前对象。
- 通过响应返回审核记录 ID、当前版号、已发布状态和锁定结果；前端保留本次已读取的内容并切为只读，立即关闭审核提交及编辑。再次读取已发布病例的服务端授权随 WP-12 检索契约接入，不提前建立管理员旁路。
- 401/403 沿用现有认证与资源授权语义，未知字段/无效检查或跨病例对象为 400，版号冲突或并发结论冲突为 409；审计失败整体回滚且不返回业务内容。
- 下线、重新启用、抽检调度与管理员管理接口不在这次 D-12 补齐范围内。

## D-41：打回重标分派与异常承接（建议）

这是已批准契约之外的新问题：提交结束了标注分派，打回不能只修改病例状态。原标注人从当前版本的 annotations.submitted 审计识别，不猜测对象创建者；空标注版本也保持同一规则。

建议正常路径：

1. 结束当前审核分派；保存批注及审核结果。
2. 复核原标注人账号、系统资格、自审双资格以及现有两级在途上限；先结束审核再计数，尤其处理自审容量。
3. 原标注人合格且有容量时，新建 annotate active 分派，病例回到“标注中”。不恢复已完成记录，不继承已过期截止时间，新分派 due_at=NULL，继续沿用不设默认期限的既定决定。
4. 原标注人不合格或容量已满时，建议保存打回结果、结束审核，将病例退至既有“待分配”，返回明确未承接原因，由既有 auto/manual/pool 模式重新分发。这个例外偏离手册正常“打回→标注中”，必须明确批准后才实施；不新增状态或超限旁路。
5. 修改后重交沿用已有完整性检查、自审/他审资格及审核分派逻辑。审核记录、版本和审计保留；不保证重交一定派给上次审核人。

不采纳异常回池时的备选：整笔打回返回 409，保留审核中及全部原数据，管理员修复原标注人的承接条件后重试。该方案不自动完成打回，无法处理原人员永久不可承接的闭环，后续须另行确认管理员重派路径。
