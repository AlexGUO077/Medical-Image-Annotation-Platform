# WP-S0 与 WP-00 启动设计

## 1. 目的与结论

本设计定义医学影像标注平台开始建设时的第一个可评审子项目。启动阶段采用两条受控工作流并行推进：WP-S0 固定安全、隐私、数据来源和未决契约；WP-00 建立不接触真实医学数据的工程骨架。两条工作流在 SG-0、SG-1 汇合，未通过安全与契约门之前，不实施依赖未决字段或接口的业务功能，也不接入真实数据。

本设计不改变源开发手册规定的产品范围、表名、字段、接口、状态机、技术路线和部署结构。发生冲突时按“源开发手册 → 需求拆解与实施基线 → UI 与交互设计要求 → 本设计”的顺序处理。

## 2. 需求来源与适用范围

实施时必须同时核对以下文件：

- `医学影像标注平台-开发手册（学生版）V1.0.docx`；
- `docs/医学影像标注平台-需求拆解与实施基线.md`；
- `docs/医学影像标注平台-UI与交互设计要求.md`；
- `docs/GitHub版本管理与回滚规范.md`。

本子项目只覆盖：

1. 契约决策、责任边界、安全设计和真实数据准入门；
2. monorepo 目录、开发环境、基础服务、前后端空壳、健康检查；
3. lint、类型检查、测试、构建和安全扫描的最小流水线；
4. 契约、决策、威胁模型和验证证据的存放结构；
5. Git 分支、提交、PR、回滚和本地工程日志纪律。

本子项目不覆盖数据库业务表迁移、账号业务实现、DICOM 导入、帧服务、标注工具、审核、检索、统计、导出或生产部署。这些能力分别由 WP-01 至 WP-17 实现。

## 3. 已冻结的启动决策

以下决策已有上位文档依据，可以用于 WP-00：

- 仓库采用单一 monorepo；
- 后端按默认主线使用 NestJS、Node 20 和 TypeScript；Node 运行时固定为 `20.20.2`；
- 前端使用 React 18、TypeScript、Vite 和 Ant Design v5；
- 后端保持模块化单体，不在 WP-00 拆分微服务；
- 业务数据库使用 PostgreSQL 16；
- DICOM 存储、对象存储、缓存/队列和全文检索分别使用 Orthanc、MinIO、Redis 7、Elasticsearch 8；
- nginx 是未来唯一公网入口，但 WP-00 只提供开发环境骨架，不宣称生产可用；
- REST 前缀为 `/api`，健康检查为 `/api/health`；
- 真实 `.env`、凭据、真实医学数据、患者信息和脱敏映射不得进入 Git；
- WP-S0 至 SG-4 放行前只允许使用合成或经确认的匿名测试数据。

Ant Design v5 已由 UI 文档选定，但必须在契约决策记录中登记，确保 D-02 在工程基线与 UI 基线之间可追溯。

2026-09-18 用户明确决定遵循源开发手册继续使用 Node 20。该决定登记为 D-38。Node 20 已结束官方维护的事实不构成安全扫描豁免；若运行时、基础镜像或依赖扫描出现严重/高危问题且没有符合项目规则的书面限时例外，WP-00 可以继续形成可评审代码，但不得通过阶段门或宣称完成。

## 4. 未决契约及阻断规则

WP-S0 建立决策登记表，逐项记录依据、选项、影响范围、责任人、批准证据和生效日期。以下事项在得到上位文件或用户确认前不得由实现人员自行固化：

- D-03 管理员 2FA 流程；
- D-04 `mask_map` 存储及密钥管理；
- D-05 标注版本历史模型；
- D-06 `key_frame_index` 表示；
- D-07 `part_id` 外键目标；
- D-08 “报告未提及”的请求表示；
- D-09 领取锁、在途上限和释放规则；
- D-10 “审核中”进入及退出时点；
- D-11 审核接口最终路径；
- D-12 缺失的管理接口；
- D-13 导出包范围与脱敏级别；
- D-14、D-32 会话撤销及浏览器凭证策略；
- D-30 至 D-37 的保留删除、来源授权、分类定级、密钥、事件响应、审计防篡改和 DICOM 去标识化配置。

阻断规则如下：

1. 未决事项不影响目录、健康检查、lint、测试框架和本地基础服务时，WP-00 可以继续；
2. 某项决定会改变字段、接口、权限、状态机或安全控制时，对应实现及下游工作暂停；
3. 文档能给出唯一答案时，记录引用并采用该答案；
4. 文档没有唯一答案时，向用户提出单一、具体、可决策的问题；
5. 决策不得只存在于聊天、代码注释或本地日志，必须进入仓库内契约记录并接受评审。

## 5. 仓库与组件设计

WP-00 建立以下顶层结构：

```text
Medical-Image-Annotation-Platform/
├── docker-compose.yml
├── package.json
├── server/
│   ├── src/
│   │   ├── main.ts
│   │   ├── app.module.ts
│   │   └── modules/health/
│   └── test/
├── web-anno/
│   ├── src/app/
│   ├── src/pages/
│   ├── src/viewer/
│   └── src/api/
├── deploy/
├── docs/
│   ├── contracts/
│   ├── decisions/
│   ├── security/
│   └── superpowers/
└── .github/workflows/
```

文件级职责在实施计划中继续细化。WP-00 不预建所有业务模块的空目录；只有健康检查和应用启动所需的最小代码进入首个增量，避免空壳模块与未来契约漂移。

### 5.1 后端空壳

后端只提供应用启动、统一 `/api` 前缀、配置加载、结构化错误的基础挂载点和 `/api/health`。健康检查区分应用存活与依赖就绪，不能用一个始终返回成功的常量响应掩盖中间件故障。

WP-00 不实现 JWT、账号、角色或业务守卫；这些属于 WP-02。安全响应头和 CORS 的开发基线可以配置，但生产来源白名单和部署策略在后续工作包完成。

### 5.2 前端空壳

前端提供应用启动、Ant Design v5 主题入口、浅色普通页面框架、暗色工作台主题令牌、路由占位和通用错误边界。页面占位不得模拟已完成的业务状态，也不得内置虚假的权限判断。

WP-00 只验证前端在 5173 端口可访问以及主题和路由基础可构建，不实现登录、任务、导入或工作台交互。

### 5.3 基础服务

开发 Compose 包含 PostgreSQL、Orthanc、MinIO、Redis 和 Elasticsearch。默认不映射到公网；开发机端口仅用于本地联调，并通过 `.env.example` 提供非秘密配置项。容器必须设置健康检查，应用启动文档明确依赖状态。

所有卷只保存本地合成测试数据。任何真实 DICOM、原始报告、患者信息或生产备份不得复制到这些卷。

## 6. 数据流与信任边界

WP-00 的数据流只包括：

```text
开发者浏览器 → Vite 开发服务器
开发者/测试 → NestJS /api/health
NestJS 健康模块 → 各本地中间件的最小连通性检查
CI → lint / typecheck / unit test / build / security scans
```

WP-00 不建立上传入口、DICOM 读取入口、对象预览入口、签名帧地址或导出路径。只要出现真实医学数据流，就视为越过本设计范围并立即停止。

WP-S0 负责绘制完整目标数据流和信任边界，至少覆盖外部浏览器、nginx、server、隔离暂存区、PostgreSQL、Orthanc、MinIO/OSS、Redis、Elasticsearch、备份、导出物和管理员访问路径。

## 7. 失败处理

- 单个中间件不健康时，就绪检查明确返回失败依赖，不把错误伪装为应用正常；
- 错误响应不包含密码、Token、连接串、内部堆栈或敏感环境变量；
- 缺少必要开发配置时应用快速失败，并给出不含秘密的配置项名称；
- CI 的 lint、类型检查、测试、构建或高严重度安全扫描失败时，PR 不得标记为可合并；
- Docker 环境不可用时，日志记录实际阻塞，不以未执行的健康检查作为完成证据；
- 审计、鉴权、脱敏等业务失败模式不在 WP-00 假实现，后续工作包按安全失败原则设计。

## 8. 测试与验收设计

WP-00 的实施计划必须采用失败测试先行，至少覆盖：

1. `/api/health` 的存活响应；
2. 依赖不健康时的就绪失败；
3. 前端路由与主题入口可构建；
4. lint、TypeScript 类型检查、单元测试和生产构建；
5. Compose 配置解析与五个中间件健康状态；
6. `.gitignore` 和秘密扫描不允许真实 `.env`、密钥、Token 或医学数据进入版本库；
7. 依赖、许可证、SAST、容器和 IaC 扫描没有未批准的严重或高危问题。

WP-S0 的验收证据至少包括：

- 责任主体、数据用途和真实数据入口状态；
- 数据分类分级和来源授权台账契约；
- 目标数据流与信任边界；
- 权限矩阵和逐资源鉴权原则；
- 威胁模型及缓解措施；
- DICOM 去标识化 profile/options 决策路径；
- 密钥、日志、事件响应和数据保留删除规则；
- 每个 P0 决策的关闭记录或明确阻断范围。

## 9. Git 与评审设计

- 文档基线先在当前 `docs/github-version-control` 分支完成远端归档和 PR 评审；
- WP-00 实现必须从最新 `origin/main` 创建 `feature/wp-00-project-skeleton`；
- WP-S0 的安全与契约文档使用独立 `security/` 或 `docs/` 分支，不与 WP-00 代码提交混杂；
- 每个提交是可说明、可验证、可回滚的单一逻辑单元；
- PR 必须填写源 Word 章节、需求基线章节、WP、S 阶段、SG 门、验证证据、安全影响和回滚方案；
- 未通过上游门、没有远端提交 SHA 或没有 PR 记录时，不宣称阶段完成；
- 已共享历史只通过 `git revert` 回退，不强制推送或改写历史。

## 10. 本地工程日志与多 Agent 协作

本地工程日志保存在 Git 仓库目录外：

`/Users/guo/College/Medical-Image-Annotation-Platform/local-engineering-log/`

每天使用一个 `YYYY-MM-DD.md` 文件。每个实际动作记录以下字段：

- 时间和时区；
- 执行者或 agent 标识；
- WP、S 阶段和 SG 门；
- 当前目标和状态；
- 正在占用或计划修改的文件；
- 完成的具体工作；
- 执行的验证命令和结果；
- 文档依据和新决策；
- 阻塞、风险和需要用户确认的问题；
- Git 分支、提交 SHA、远端和 PR；
- 下一步与交接说明。

多 agent 编码时，任何 agent 修改共享文件前必须先查看当天日志中的“文件占用”记录，并登记自己的文件范围。共享契约、根配置、锁文件、迁移序列、Compose、CI 和公共类型属于高冲突文件，同一时间只允许一个 owner 修改。日志用于协调和恢复上下文，但不替代 Git 提交、契约文档、测试证据或 PR。

## 11. 实施入口

用户批准本设计后，下一步分为两个独立计划：

1. WP-00 文件级实施计划：工程骨架、健康检查、前端空壳、Compose、CI 和安全扫描；
2. WP-S0 文档实施清单：决策登记、数据流、权限矩阵、威胁模型和安全门证据。

两个计划可以并行执行，但 WP-00 只使用合成数据且不得固化第 4 节未决契约。WP-01 及其后续工作在 SG-0、SG-1 和 WP-00 验收通过前不得开始。
